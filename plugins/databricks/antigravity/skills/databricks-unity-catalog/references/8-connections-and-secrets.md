# Connection credentials and secrets

## A connection's password

- Give it as `password secret('<scope>', '<key>')` in `OPTIONS`, from a workspace secret scope ([CREATE CONNECTION](https://docs.databricks.com/sql/language-manual/sql-ref-syntax-ddl-create-connection) says to use the secret function for any credential).
- After each rotation, update the scope (a Databricks-backed one: `databricks secrets put-secret <scope> <key>`; a Key Vault-backed one: in the vault), then run `ALTER CONNECTION <name> OPTIONS (<every option, as at create>, password secret('<scope>', '<key>'))` for every connection that uses it, from a workspace that has the scope. Take the option list from the `CREATE CONNECTION` or the code that made it: `DESCRIBE CONNECTION` shows only "a selective list of options that are considered safe to display". Show the statement to the user before running it, then test the connection with a read; if the read fails, run the `ALTER` again with the full list. `secret()` is read when the statement runs (`OPTIONS` take constant expressions only), so run it after every rotation; a connection that fails to log in after one (password authentication fails) needs this `ALTER`.
- A connection made with `databricks connections create`, the API or Catalog Explorer (Lakeflow Connect connections are) holds the password itself in its options (no `secret()`). Rotate it with `databricks connections update <name> --json @<file>`, the file (mode 600) holding `{"options": {<every option>, "password": "<new>"}}`, deleted in the same command.
- `CREATE`/`ALTER CONNECTION` with `secret()` fails with `INVALID_SQL_SYNTAX.OPTION_IS_INVALID ... only constant expressions are supported` when the secret can't be read (missing scope or key, vault unreachable). `SELECT secret('<scope>', '<key>')` shows the real error (`INVALID_SECRET_LOOKUP` when the key can't be retrieved).

## Where the secret lives

Setup of the vault itself (roles, tenants, networking, IAM policies) is on the docs pages: [Workspace secret scopes](https://docs.databricks.com/security/secrets/workspace-secret-scopes) (on Azure, its Azure Key Vault-backed section) and [Configure external secrets](https://docs.databricks.com/security/secrets/configure-external-secrets) (Beta). Two traps agents get wrong:
- **Azure Key Vault-backed scope:** only the vault's **Vault access policy** permission model works, not Azure RBAC; no role assignment makes an RBAC vault work. Switch the vault (or use another) to access policies, or keep the password in a Databricks-backed scope. A vault in another tenant works if the user creating the scope can create service principals in that tenant (otherwise `403 Authorization_RequestDenied`). AWS has no Secrets Manager-backed scope: use a Databricks-backed one.
- **External secrets on AWS Secrets Manager:** `secretsmanager:ListSecrets` can't be limited to a resource, so the backed schema would list every secret name in the account and region. Limit the import with the connection's tag filter (`tag_key`, `tag_value`), and the reads to the secret's ARN or a `secretsmanager:ResourceTag` condition on `DescribeSecret` and `GetSecretValue` (the page's policy). Names map `/` to `|` and `.` to `:` (`app/pg-password` is `<catalog>.<schema>.app|pg-password`).
